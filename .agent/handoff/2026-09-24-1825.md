## 試したこと・結果

### 成功したアプローチ

- **送信内容を手で組み立てず、画面の実フォームを丸ごと送る**
  `navigateToContactRegister()` → `form.submittype.value='save'` → `new FormData(document.forms.EditView)` を fetch で POST。
  これにより hidden（`module` / `action=EW_AN` / CSRF トークン）と画面が入れる既定値
  （`favorite_school_id` は**環境ごとに違う UUID**、`favorite_area_id=60`、`bank_payment_type=2` 等）を取りこぼさない。
  84 項目の手写しも、CSRF トークンを読むコードも不要になった。
- **成功判定は `res.ok` ではなく `record=` の有無**。保存失敗時も 200 で登録画面が返るため。
- **失敗理由はエラー枠→本文の順で拾う**。`#top_err_info_msg_div` が空でも本文に理由が出る画面がある（重複確認画面）。
- **削除は UUID を明示列挙**。「検索ヒットを全部消す」書き方は auto mode のガードに止められた（Unverifiable Deletion Scope）。読み取り専用で対象確定 → UUID 指定で削除、の 2 段階に組み直して通った。

### 失敗したアプローチ（理由）

- **ふりがなをカタカナで送信** → サーバーが却下（全角ひらがな必須）。CSV `contact_register_data.csv` と同じ値にすべきだった。
- **`bank_payment_type` を既定値 2（イオンCカード）のまま送信** → カード情報が必須になり却下。最小限登録は `3`。
- **同姓同名で再送** → 「二重登録の可能性のある受講生一覧」が返り保存されない。動作確認ランナーは名を実行時刻で一意にして回避。
- **姓のプレフィックス検索（`API`）で一覧を引く** → 0 件。候補生/受講生一覧の姓検索は**完全一致**。姓はフルで指定する必要がある（日本語を環境変数で渡すと化けるのでソースに持たせた）。

### ⚠️ 前提が崩れた発見

1. **この方式で作られるのは候補生ではなく「受講生」。**
   掃除のため検索したら候補生一覧に 0 件、受講生検索に出てステータス列が「受講生」だった。
   URL の `contact_status=5` は送信内容に含まれないため。
   → **`gessya_ikkatu_setup_test.js` の前提データ（候補生→受講生へ昇格）には使えない。** 横展開先の第一候補が外れた。
   → UI の保存ボタンも同じ内容を送るので挙動は同じはずだが、**UI 経由での確認は未実施**。
2. **既存 UI テスト `tests/shimamura/flow/contact_register_test.js` の正常系が、登録できていないのに合格している。**
   成功判定が `I.dontSee('は必須', ...)` だけで、CSV の姓名が固定値（テスト/太郎）のため 2 回目以降は
   二重登録の警告画面に飛ぶが、そこに「は必須」は無いので通る。
   実際に今回の実行で保存された `CONTACT_REGISTER_success.png` は二重登録の警告画面だった（目視確認済み）。
