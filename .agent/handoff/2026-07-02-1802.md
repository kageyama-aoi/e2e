## 試したこと・結果

### 成功したアプローチ
- **運営管理費の概念**: 同一店舗内で最大額の運営管理費コースを1件だけ確定し、既存額より高い場合は赤処理（マイナスで打消し）→再作成、というロジックを実機で確認。
- **クラス⇔コースの紐づけ手順**（UIから発見、DBスキーマや裏側の仕様書は無し）:
  1. コース(ShimaCourse)を `module=ShimaCourse&action=EditView` で作成（course_cd, course_name, course_category, course_kanrihi）
  2. クラス(Course)を `module=Course&action=EditView` で作成（name, area_id→school_idはAJAX連動, course_category, 曜日, 時間, 定員）
  3. クラス詳細画面の「コース」タブ → 「コース選択」ポップアップでコース検索 → 選択 → 「コース適用」ボタンで紐づけ
  4. クラス詳細画面の「スケジュール」タブ → 「全体スケジュールの作成・変更」で実スケジュールを作成しないと、経理ビュー登録時に「クラスにスケジュールが設定されていません」エラーになる（曜日チェックボックスだけでは不十分）
- testgcp環境に運営管理費1000円・1400円それぞれ単一コースの検証用クラスを新規作成済み（店舗: 706:ウォークテス前橋店、既存の「ピアノ水曜日_02」と同一店舗）
  - クラス「E2Eテスト_ピアノ運管費1000」(kanrihi=1000) / コース TCE00002
  - クラス「E2Eテスト_ピアノ運管費1400」(kanrihi=1400) / コース TCE00001
- **検証方法**: 経理カルテビュー（`module=Student&action=DWCarteKeiri_AN`）上部の未払いバナー（`#top_err_info_msg_div`、同一IDで複数存在するため `querySelectorAll` で取得）に `料金名: 月運営管理費（N月） 未払分: X円 クラス名: Y` という形式で確定額・クラス名が明示されている。金額は税込表示（マスタは税抜、×1.1で比較）。`verifyKanrihiFee`（`TsukihiIkatsuFlowPage.js`）として実装・PASS確認済み。
- **既存バグの発見**: クラス選択ポップアップ（`ShouldBeOnClassSelectPopup`）は前方一致検索なのに無条件で検索結果1件目をクリックしており、無関係の類似名クラス（例:「ピアノ水曜日_02e」）を誤選択する事故が起きていた。`class_name01` と完全一致する行のみクリックするよう修正（#168）。既存シナリオ001-007で回帰なし確認済み。

### 【重要】月謝一括作成バッチ検証における発見
- `tsukihi_ikatsu_setup_test.js`（経理ビューEで確認完了する登録フロー）は、**登録した「今月」だけでなく「来月」分の運営管理費も、登録時点で自動的に先読み作成する**ことが判明（`#tbl_carte` で確認：削除前は登録直後から2026/08が既に1,540円だった）。
- そのため `tsukihi_ikatsu_test.js`（月謝一括作成バッチのテスト）を実行しても、バッチが何もしなくても来月分は既に存在しており、**バッチ固有の効果を区別できない**。既存の `verifyMonthlyFees` の `I.see(targetYearMonth)` チェックも、同じ理由で以前から実質的に「常に真」だった可能性が高い。
- 検証のため、来月（8月）分の運営管理費・月謝Feeレコード5件を`module=Fee&action=DW_AN&record=<id>`の「削除」ボタンで確実に削除 → `#tbl_carte`で0円を確認 → 月謝一括作成バッチを実行 → **再確認したが8月分は0円のままで、バッチは再作成しなかった**。
- 結論（推測）：バッチには何らかの「この学生の来月処理は済み」というべき等性/スキップ判定があり、Feeレコード単体を消しても再作成されない。バッチ固有の動作を検証するには、**一度も経理ビューEを通っていない「新鮮な」学生・クラスの組み合わせ**が必要（今回作成した検証用クラスは既にscreen Eを通過済みなので使えない）。
- ユーザーの提案（削除して確かめる）は正しかったが、削除だけでは「バッチが正しく動く」ことの証明にはならず、むしろ「バッチは重複防止で動かない」という別の重要な仕様を発見する結果になった。

### 失敗したアプローチ（理由）
- 「既存クラス『ピアノ水曜日_02』に紐づく3コース（1000円/1400円/150000円）のうち、検索ポップアップで特定のコースを選んで登録する」→ 失敗。経理ビューBのクラス選択ポップアップはクラス単位でしか選べず、どのコース（料金ティア）が採用されるかは選択不可（内部で自動的に最大額が採用される）。→ 単一コースにリンクした専用クラスを新規作成する方針に転換。
- 「コース(ShimaCourse)詳細画面の『クラス編集』ボタンでクラスと紐づける」→ 失敗。このボタンは常にログインユーザーのデフォルト店舗を渡すだけの汎用ショートカットで、閲覧中のレコードとは無関係だった。→ クラス詳細画面の「コース」タブから紐づける方法を発見（ユーザーからのヒントで判明）。
- `verifyKanrihiFee` の初期実装（経理カルテビューの「コース一覧」サブパネルの運営管理費列を見る）→ そこは契約時の名目値であり、実際に確定した金額・赤黒処理の結果を反映していなかった。→ 「入出金」サブパネルおよび画面上部の未払いバナーが実際の確定額を持つと判明。
