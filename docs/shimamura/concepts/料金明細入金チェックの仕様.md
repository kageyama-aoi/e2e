## ① 画面の概要

- 画面: `index.php?module=SalesGroup&action=EditView&record=<明細番号>&transfer=1&salesno_contactid=<受講生>`
  （経理ビュー個人の明細番号リンクから遷移）
- 1行 = 同じ明細番号（`salesno`）を持つ入出金（`sms_transaction`）1件。
  経理ビューで複数の料金を一度に確定すると、同じ明細番号の行が2行以上できる
  （例: 分類「スクール」のクラスなら月謝と運営管理費が同じ明細番号になる）。
- 上段: 入金日・入金額・手数料・支払方法を入れ、「バランスを入力」（`CopyBalance`）→「入金分配」（`DivideTransfer`）で各行に配る。
- 保存: 画面側チェック（DT-01）→ POST → 明細全体のサーバーチェック（DT-02）→ 行ごとのサーバーチェック（DT-03）→ DB 更新。
- 送る値: 入力欄の行は保存の瞬間の入力欄の値。**支払方法の値の決まり方は DT-04**、入金分配で値がどう変わるかは DT-05。

### 行の描き方は2種類ある 🔵

| 行の種類 | 条件 | 画面 | 送る値 |
|---|---|---|---|
| 入力欄の行 | 入金日が空、または 入金日 ≥ 締日 | `t_date_0` などの入力欄 | 保存の瞬間の入力欄の値 |
| 文字表示の行 | 入金日あり かつ 入金日 < 締日（`transaction_array.shimebi`） | 文字だけ。入力欄なし | DB の値。ただし支払方法と、DB で数値の 0 の項目は空文字 |

締日 `shimebi` は testgcp で `2001-01-01`（実質なし）。ユーザー談（2026-10-01）では運用上の「締め日」は無いので、**文字表示の行は通常は出ない**。
DT-01 の C1・DT-04 の C11 は、締日が設定された環境だけで Y になる。

条件のまとまり × 動作のまとまりで、「条件を変えると動作の結果が変わるか」を見た。● 変わる、△ 評価されるかどうかだけが変わる、· 関係なし。

|---|---|---|---|---|---|

| C4〜C5 | · | ● | △ | · | · |
| C6〜C10 | · | ●（C5 を通して） | ● | · | · |
| C11〜C12 | · | · | · | ● | · |
| C13〜C16 | · | · | · | · | ● |

- C1〜C3 は「サーバーに送られるか」、C4 は「行ごとのチェックまで進むか」だけを決める（△）ので、**DT-01 → DT-02 → DT-03 は入れ子**（ガイド 2-B）にした。


## ⑦ 問い合わせとの対応

> 同一の料金明細番号で入金済みの項目があった場合、日をまたぐと入金記入画面で入金処理できない。
> 例: 6・7月分が同じ明細番号で、6月分のみカード請求済み → バランスを入力＞入金分配＞保存 で入金済みエラー

**testgcp で再現した（2026-10-01・TC-34〜36）。** 明細番号 70600000320（4行）の1行目をカードで入金済みにして、
バランスを入力 → 入金分配 → 保存したところ「既に入金済みのため、入金処理は不可です(料金名:月運営管理費（11月）)」になり、保存されなかった。

| 段階 | 起きること | 表 | 根拠 |
|---|---|---|---|
| 画面を開く | 6月分（カードで入金済み）の支払方法 `card` が選択肢（現金・空）に無いので、「現金」が選ばれた状態で表示される | DT-04 R3 | 🔵🟢 |
| 入金分配 | 7月分（未入金）に配られる。6月分（入金済み・バランス 0）は変わらない | DT-05 R2・R8 | 🔵🟢 |
| 保存（画面側） | チェックを通って送信される | DT-01 R5 | 🟢 |
| 保存（サーバー） | 6月分の支払方法が `card` → `cash` で差分あり → Check2。明細全体が保存されない | DT-03 R4 → DT-02 R2 | 🟢 |

- **入金分配は関係ない**。分配せず未入金の行を手で入力して保存しても、同じエラーになった（TC-35 🟢）。
- **入金済みの行があるだけでは起きない**。1行目が現金入金済みなら、同じ操作で保存できた（TC-36 🟢）。カード等、画面の選択肢に無い支払方法で入金済みのときだけ起きる。
- 「日をまたぐと」: カード請求した当日は、入金結果が反映される前で6月分がまだ入金済みになっていない（または POS 送信中で DT-02 R1）。翌日に入金結果が反映されてカードで入金済みになると DT-04 R3 に当たる、と考えている 🟡（要確認）。
- 「以前はできていた」: 支払方法の選択肢まわり（JS の `Clark 93812` コメント）と Check2（TR 93812 / 92110）が後から入ったため、と考えられる 🔵🟡。
- 締日（文字表示の行）による別の経路（DT-01 R1・DT-04 R1）は、締日が設定された環境だけで起きる。
