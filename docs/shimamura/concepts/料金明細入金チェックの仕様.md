## ① 画面の概要

- 画面: `index.php?module=SalesGroup&action=EditView&record=<明細番号>&transfer=1&salesno_contactid=<受講生>`
  （経理ビュー個人の明細番号リンクから遷移）
- 1行 = 同じ明細番号（`salesno`）を持つ入出金（`sms_transaction`）1件。
  経理ビューで複数の料金を一度に確定すると、同じ明細番号の行が2行以上できる
  （例: 分類「スクール」のクラスなら月謝と運営管理費が同じ明細番号になる）。
- 上段: 入金日・入金額・手数料・支払方法を入れ、「バランスを入力」（`CopyBalance`）→「入金分配」（`DivideTransfer`）で各行に配る。
- 保存: 画面側チェック（DT-01）→ POST → 明細全体のサーバーチェック（DT-02）→ 行ごとのサーバーチェック（DT-03）→ DB 更新。
- 送る値: 保存の瞬間に画面の各行に入っている値。**支払方法の値の決まり方は DT-04**、入金分配で値がどう変わるかは DT-05。

### 用語（この資料で使う言葉）

この資料は設計書ではなく、画面の動き・コード・共有資料から作ったもの。根拠の記号（🟢🔵🟡）で確かめ方を区別している。

**行**: 画面の下半分の1行 ＝ 入出金（`sms_transaction`）1件。料金ごとに1件ある（例: 月謝（10月）、運営管理費（11月））🟢。

**行が持つ項目**（どれも、その入出金1件の値）

| 画面の列 | 業務の意味 | 項目名 | いつ入るか |
|---|---|---|---|
| 契約日 | クラスの契約日（と推測。テストデータでは契約日を入れて作っている）🟡 | — | 経理ビューで確定したとき。この画面では変えられない |
| 入金予定額 | 払ってもらう予定の金額 🔵 | `in_amount` | 確定したとき |
| 締切日 | その料金の**支払期限** 🔵 | `due_date` | 確定したとき。この画面で変えられる |
| 入金日 | 実際に入金があった日。未入金なら空 🔵🟢 | `t_date` | 入金を記録したとき（この画面に限らない） |
| 入金額 | 実際に入金された金額。未入金なら 0 🔵🟢 | `actual_in_amount` | 同上 |
| 手数料 | 入金の手数料 🔵 | `commission` | 同上 |
| 支払方法 | 現金・カードなど。未入金なら空 🔵🟢 | `payment_type` | 同上 |

**入金済みの行**: 入金日・入金額・支払方法のどれかに値がある行（サーバーの判定。共有資料の要約による 🟡）。どの画面で入金したかは関係ない。

**締日**: 経理の締めの日付。**行ごとの「締切日」とは別物**で、システム全体で1つの値。

| | 締切日 | 締日 |
|---|---|---|
| 何の日付か | 行ごとの支払期限 | 経理の締めの日付（システム全体で1つ） |
| どこにあるか | 入出金1件ずつ（`due_date`） | 画面を開いたときにサーバーが画面のデータに埋め込む値（`transaction_array.shimebi`） |
| 画面に見えるか | 列として見える | 見えない。設定する画面も見当たらない（ユーザーは変えられない）🟢 |
| testgcp の値 | 行ごとに違う | `2001-01-01`（2026-10-14 確認 🟢） |

締日の使い道は「**入金日が締日より前の行を、編集できない行にする**」判定だけ 🔵🟢。
testgcp の締日は 2001-01-01 で、ユーザー談（2026-10-01）では本番にも運用上の締め日は無い。
2001 年より前の入金日はテストデータでもありえないので、**普段の画面ではすべての行が編集できる**。
締日の値がサーバー側のどの設定から来るか（システム管理者だけが触れる設定か、設定ファイルか）は未確認。

### 締日より前に入金済みの行は編集できない（普段は起きない）🔵

| 行の種類 | 条件 | 画面 | 送る値 |
|---|---|---|---|
| 編集できる行（普段はすべての行） | 入金日が空、または 入金日 ≥ 締日 | 入金日・入金額などが入力欄（`t_date_0` 等） | 保存の瞬間の入力欄の値 |
| 締日より前に入金済みで編集できない行 | 入金日あり かつ 入金日 < 締日 | 値が文字で表示されるだけ | DB の値。ただし支払方法と、DB で数値の 0 の項目は空文字 |

DT-01 の C1・DT-04 の C11 は、この行があるときだけ Y になる。本番・testgcp では起きないので、
テストでは画面の中だけ締日を書き換えて観察する **TC-101（100番台＝異質なケース）** だけで扱う。

## ⑦ 問い合わせとの対応

> 同一の料金明細番号で入金済みの項目があった場合、日をまたぐと入金記入画面で入金処理できない。
> 例: 6・7月分が同じ明細番号で、6月分のみカード請求済み → バランスを入力＞入金分配＞保存 で入金済みエラー

**testgcp で再現した（2026-10-01・#280 #284。自動テストでは TC-14）。** 明細番号 70600000320（4行）の1行目をカードで入金済みにして、
バランスを入力 → 入金分配 → 保存したところ「既に入金済みのため、入金処理は不可です(料金名:月運営管理費（11月）)」になり、保存されなかった。

| 段階 | 起きること | 表 | 根拠 |
|---|---|---|---|
| 画面を開く | 6月分（カードで入金済み）の支払方法 `card` が選択肢（現金・空）に無いので、「現金」が選ばれた状態で表示される | DT-04 R3 | 🔵🟢 |
| 入金分配 | 7月分（未入金）に配られる。6月分（入金済み・バランス 0）は変わらない | DT-05 R2・R8 | 🔵🟢 |
| 保存（画面側） | チェックを通って送信される | DT-01 R5 | 🟢 |
| 保存（サーバー） | 6月分の支払方法が `card` → `cash` で差分あり → Check2。明細全体が保存されない | DT-03 R5 → DT-02 R2 | 🟢 |

- **入金分配は関係ない**。分配せず未入金の行を手で入力して保存しても、同じエラーになった（#284 🟢。自動テストの TC-14 も手入力）。
- **入金済みの行があるだけでは起きない**。1行目が現金入金済みなら、同じ操作で保存できた（#284 🟢。自動テストでは TC-15 で、現金入金済みの明細が保存できることを確かめる）。カード等、画面の選択肢に無い支払方法で入金済みのときだけ起きる。
- 「日をまたぐと」: カード請求した当日は、入金結果が反映される前で6月分がまだ入金済みになっていない（または POS 送信中で DT-02 R1）。翌日に入金結果が反映されてカードで入金済みになると DT-04 R3 に当たる、と考えている 🟡（要確認）。
- 「以前はできていた」: 支払方法の選択肢まわり（JS の `Clark 93812` コメント）と Check2（TR 93812 / 92110）が後から入ったため、と考えられる 🔵🟡。
- 締日（締日より前に入金済みで編集できない行）による別の経路（DT-01 R1・DT-04 R1）は、締日が設定された環境だけで起きる。

### 再現のしかた（testgcp）

- **データ作成**（受講生を1人使う。約1分）:

  入金分配の代わりに未入金の行へ手で入力するときは `OBS_MODE=manual` を付ける（#284）。

### 対策の方向（開発側への提案。未検討）

- 画面: 支払方法の選択肢に、DB にある値（カード等）を表示用に含める（DT-04 R3 をなくす）
- サーバー: 入金済みの行の支払方法は、画面から変えられない値として比較から外す
- 画面: 編集できない行も支払方法を `sales_arr` に持たせる／`CheckForBlankFields()` で入力欄の無い行を飛ばす（DT-01 R1・DT-04 R1）
- 入金分配: 余りを入金済みの行に足さない（DT-05 R7）
